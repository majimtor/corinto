# 0013. Webhooks following Standard Webhooks

- Status: accepted
- Date: 2026-11-14
- Deciders: the maintainer

## Context

Conversions reach Corinto from other systems, and later Corinto will notify
other systems. A signature format in use by a client is expensive to
change.

Facts checked on 2026-11-12 and 2026-11-13. The Standard Webhooks
specification, version 1.0.0 under Apache-2.0, defines the headers
`webhook-id`, `webhook-timestamp` and `webhook-signature`, an HMAC-SHA256
over `id.timestamp.body`, secrets of 24 to 64 bytes serialised with the
prefix `whsec_`, and a signature list that allows rotation. It leaves the
timestamp tolerance open; its reference library uses five minutes. OWASP's
webhook security cheat sheet recommends a documented scheme of this kind
and cites it. The official Go library has a single tag, 0.0.1.

## Decision

Standard Webhooks 1.0.0 in both directions. The signature is implemented by
hand against the specification, with test vectors, because the official Go
library is too young to depend on.

Inbound, a source belongs to a workspace and is authenticated by its
signature alone, verified over the body as received. Its secret is
generated by Corinto and stored encrypted, since verifying an HMAC needs it
in clear. Replays are bounded by a timestamp tolerance and by remembering
identifiers. The payload schema is closed, so there is no field where
personal data could travel.

Outbound, each destination has its own secret, and a delivery is treated
as a call to an address somebody else chose: retried, bounded and checked
before connecting.

PLAN.md section 6 specifies both directions: sizes, tolerances, responses,
the retry mechanism and what is logged.

## Alternatives considered

- A signature format of the project's own. Full control. Every sender
  would have to learn it, and its mistakes would be new ones.
- Asymmetric signatures (`v1a`, Ed25519). Corinto would store only a public
  key. Few senders offer it.

## Consequences

- Positive: senders can use existing libraries; replay, duplicates and
  rotation have defined behaviour.
- Negative: a hand-written implementation of the scheme has to be kept
  correct by its tests.
- Strongest argument against: a shared secret encrypted in the database can
  be recovered by whoever obtains both the database and the environment
  key.

## Reopen when

A sender offers asymmetric signatures, or the official Go library reaches a
stable release, in which case it replaces the hand-written one.
